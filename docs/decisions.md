# Decisions

Each entry says what was chosen and why.

1. **One generic renderer per platform, driven by an IR, instead of native code per widget.** An NSH app is TSX or Rust; asking it to write SwiftUI and RemoteViews for every widget defeats the point. The app writes a tree of primitives (Widget Tree IR v1, [ir.md](ir.md)) and data; `NshWidgets.swift` and `NshWidgets.java` draw any tree. A new widget is new data, not a new native build. The cost is that the IR offers only what every renderer can draw, and platform gaps show up as fallbacks ([capabilities.md](capabilities.md)).

2. **Two TS layers: base and kit.** `base.ts` holds the primitives, the class resolver and theme tokens, with no look of its own, as `nsh/base` is to NSH apps and gpui-base to GPUI Kit. `kit.ts` holds styled components built only from base nodes. The kit can grow and restyle without touching a renderer, and an app that wants its own look skips the kit.

3. **`widgets.json` beside `nsh.json`.** NSH warns about `nsh.json` keys it does not know, so the App Group and the kinds live in their own file. `nsh-widgets build` writes only the keys NSH itself reads (`ios`, `macos`, `android.libraries`) into `nsh.json`.

4. **Android provider slots with the kind as meta-data.** Android names an `AppWidgetProvider` by its class, and a prebuilt library cannot compile a class per app kind. The AAR ships `NshWidgetProvider$Slot1` to `$Slot16`; the app's manifest gives each kind a slot and names the kind in the receiver's `dev.supernsh.widgets.kind` meta-data. Sixteen slots set the limit of 16 kinds; WidgetKit bundles group ten widgets per block, so two blocks cover them.

5. **The app's per-kind AAR is generated by the CLI and merged by NSH.** The crate's AAR holds what every app shares: renderer, layouts, icons, slots and the action receiver. What differs per app (the slot receivers, `appwidget-provider` XML per kind, description strings) goes into `.nsh-widgets/android/nsh-widgets-app.aar`, which `build` lists in `nsh.json` `android.libraries`. NSH merges both manifests when it packages the app.

6. **One writer per file, atomic renames, an action inbox the app drains.** `snapshot.json` is written only by the app. `data.json` is written by the app and by widget buttons, always through a temporary file and a rename, so neither side reads half a file. Presses append to `actions.jsonl`; `take_actions` moves it aside before reading, so each event is returned once and a press during a read starts a new inbox. Widget events carry a UUID so the app can tell them apart. `update_data` merges top-level keys so an app update does not overwrite a key the widget just changed, unless the patch names it.

7. **System font on Android.** RemoteViews cannot set a typeface, and bundled and downloadable fonts both failed in the widget's restricted inflation context. Android widgets use `sans-serif` with the IR's weight. Fonts in `widgets.json` apply to iOS and macOS only.

8. **iOS toggles as checklist rows.** A WidgetKit `Toggle` draws only a tinted pill that hides a tinted label when on, and forcing `.switch` shows the unsupported placeholder. A button with a check circle, run through the same App Intent, reads clearly in both states. Android 12+ gets a real `Switch`.

9. **Build the extension without an Xcode project.** `nsh-widgets build` runs `swiftc -application-extension` with `-Xlinker -e -Xlinker _NSExtensionMain` (without that entry point the extension crashes in Apple's extension bootstrap), then `xcrun appintentsmetadataprocessor` for the App Intents metadata (without it a widget button fails with "There is no metadata"). The renderer and a generated `WidgetBundle` are the only sources. No `.xcodeproj` to generate, check in or keep in sync.

10. **Require NSH main after longbridge/nsh#2879.** Embedding an app extension needs `ios.extensions` and `macos.extensions` in `nsh.json`, merged on 2026-11-23, and Android needs `android.libraries` with AAR manifest merging. The NSH 0.6.0 release has neither, so the library targets NSH main at or after `5aa56b19` (or the nightly) until a release ships them.

11. **The repository root is the nshm.** NSH installs a git nshm from the repository's root and has no way to name a subdirectory. So the crate lives at the root (with the CLI as a second workspace member), and the root `nsh.json` exports the TypeScript in `packages/nsh-widgets/src` as `nsh-widgets`, `nsh-widgets/base` and `nsh-widgets/kit`. An app adds one dependency and gets the Rust module, the AAR and the TSX modules together; NSH versions come from the repo's tags. The crate's `include` list keeps the published crate to what builds it.

12. **Android gradients as bitmaps.** RemoteViews can set a view's colour but no gradient drawable. A container with a gradient is wrapped in a `FrameLayout` whose `ImageView` stretches a small bitmap drawn with `LinearGradient`; the root has such an `ImageView` behind its content. The bitmap is drawn for the current light or dark mode, so a mode change shows at the next redraw. Non-container nodes keep the first-colour fallback.

13. **WidgetKit content margins off.** WidgetKit adds its own margins that Android has no equivalent of, and earlier builds dropped the root's padding on iOS. The widget configuration calls `contentMarginsDisabled()` and the renderer applies the root's `pad` (16 by default), so a tree is padded the same everywhere.

14. **Lock-screen widgets take their own tree.** A home-screen tree does not fit a 76-point circle. The snapshot carries an optional `accessory` tree for `circular`, `rectangular` and `inline`, and `circular:hidden` style classes trim it further. The same tree is the bar text of `show --format waybar`, the compact Dynamic Island of a Live Activity, and a KDE plasmoid in a panel.

15. **`preview` and `show` draw in the CLI, not in a fourth native renderer.** They exist to check a layout and its data without a device, and to put a widget in a terminal or Waybar where no widget host exists. They follow the native renderers' rules but are not the reference.

16. **One Live Activity type for every kind, its attributes declared twice and matched by name.** ActivityKit needs an `ActivityAttributes` type in the app (to request the activity) and in the widget extension (to draw it), and pairs the two by type name and shape. The app's copy is in the crate's `swift/Bridge.swift`, the extension's in `NshActivities.swift`; both are `NshActivityAttributes` with a `kind` and a JSON `data` string. One generic type draws any kind from its snapshot, so an activity needs no Swift from the app. ActivityKit is `@_weakLinked` in the bridge, because NSH apps run from iOS 15 and ActivityKit starts at 16.1; the calls check for iOS 16.2 at run time and otherwise return `unsupported`.

17. **Options as data overlays.** A configurable widget could have taken a parameter per field. Instead each value names an object in the kind's data, and the renderer lays that object over the data and sets `{option}`. The tree stays one tree, the app feeds every value's data in one `update`, and the IR gains no node. iOS and macOS need a concrete `AppEnum` and `WidgetConfigurationIntent` per kind, so `build` generates them from `widgets.json`; Android stores the choice per placed widget and reads the values from the slot's meta-data.

18. **Android tile slots, like provider slots.** Android names a `TileService` by its class, as it names an `AppWidgetProvider`. The AAR ships `NshTileService$Slot1` to `$Slot8`, and the app's generated manifest gives each control a slot with its data kind, key or action, label and icon as meta-data. Eight slots set the limit of 8 controls.

19. **Android lists through `RemoteCollectionItems` on the root views.** `setRemoteAdapter` with `RemoteCollectionItems` (API 31) builds a scrolling list without a `RemoteViewsService`, but Android applies it only on the views passed to `updateAppWidget`, not on views nested with `addView`. The renderer builds the list's items while it walks the tree and sets them on the root views, against the list layout's id. Only one list per widget can do that; later lists, and every list before API 31, draw the first `max` items like iOS.

20. **The KDE host reads through the CLI.** A plasmoid's QML cannot read arbitrary files without a C++ plugin, and a compiled plugin would tie the package to one Plasma and Qt build. The generated plasmoid runs `nsh-widgets show --format ir` and `nsh-widgets apply` through Plasma's executable data engine instead (`PlasmaCore.DataSource` on Plasma 5, `P5Support.DataSource` on 6). The CLI already knows the store layout and the action vocabulary, so the plasmoid is plain QML and the store keeps one writer implementation per platform. The cost is polling: the plasmoid reads every two seconds.
